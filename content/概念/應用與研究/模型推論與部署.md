# 模型推論與部署

> LLM 模型從訓練完成到實際服務使用者的過程：推論優化、部署架構、成本控制。

## 推論 vs 訓練

| 階段 | 特點 | 成本 |
|------|------|------|
| 訓練 | 大量 GPU、長時間、一次性 | 極高 |
| 推論 | 每次請求都需計算、持續性 | 中等但累積 |

## 推論優化技術

| 技術 | 效果 | 詳見 |
|------|------|------|
| [[flash-attention\|Flash Attention]] | 減少 HBM↔SRAM 搬運，加速 8-9x | 專文 |
| [[kv-cache\|KV Cache]] | 避免重算 K/V，省記憶體 | 專文 |
| GQA/MLA | 減少 KV Cache 佔用 | KV Cache 文 |
| 量化（Quantization） | 降低精度換取速度和記憶體 | — |
| Speculative Decoding | 小模型猜大模型的輸出 | — |
| [[rtk-ai-rtk\|RTK]] | 減少送給 LLM 的 token 數 | 專文 |

## 部署架構

| 架構 | 適用場景 |
|------|----------|
| 單機 GPU | 開發、小規模 |
| 多 GPU (Tensor Parallel) | 大模型推論 |
| 多節點 (Pipeline Parallel) | 超大模型 |
| Serverless | 間歇性流量 |
| 邊緣部署 | 隱私需求、低延遲 |

## 推論服務框架

| 框架 | 特色 |
|------|------|
| vLLM | PagedAttention，高吞吐 |
| TGI (HuggingFace) | HuggingFace 官方 |
| Triton Inference Server | NVIDIA 官方 |
| Ollama | 本地推論，簡單易用 |
| [[litellm\|LiteLLM]] | 統一 API 代理 |

## 成本控制

- [[rtk|RTK]]：減少送給 LLM 的 token（60-90% 節省）
- Cache Input：共用前綴的 KV Cache（OpenAI 打 1 折）
- 模型選擇：簡單任務用小模型，複雜任務用大模型
- Batch API：非即時請求用批次處理
